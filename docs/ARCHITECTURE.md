# GIAMS — Architecture

> Supersedes the initial plan. Revised for: offline operation, LAN survivability,
> cloud sync, and an eventual subscription/SaaS model.
> Domain reference: [`coa-lgu-accounting-reference.md`](coa-lgu-accounting-reference.md)

---

## 1. The four requirements that shape everything

1. **Works offline.** A clerk with no internet must still be able to work.
2. **Works on LAN without internet.** If the office WiFi is up but the internet is
   down, *all* users must still transact against the same data.
3. **Syncs to cloud Postgres**, manually or automatically, **with strict duplication
   prevention.**
4. **Becomes a subscription product**, with expiry enforced even when offline.

Plus the standing rule from the contract: money is computed **on the server** with
**exact decimal arithmetic**, entries must **balance**, and the audit trail must be
**immutable and tamper-evident**.

## 2. Three tiers, one authority

The mistake that kills offline accounting systems is treating every device as a peer
and trying to merge ledgers afterward. Two clerks posting the same voucher offline
produce two ledger facts, and no merge algorithm can decide which one is real.

So: **many devices may hold data, but for any given municipality exactly one node may
create a ledger fact.**

```
┌─ Workstation (Tauri) ─┐   ┌─ Workstation ─┐   ┌─ Workstation ─┐
│ SQLCipher local DB    │   │               │   │               │
│ · drafts              │   │               │   │               │
│ · cached reference    │   │               │   │               │
│ · cached reports      │   │               │   │               │
│ · outbox              │   │               │   │               │
└───────────┬───────────┘   └───────┬───────┘   └───────┬───────┘
            │        LAN / mDNS discovery (no internet needed)
            └───────────────────────┼───────────────────┘
                                    ▼
                    ┌───────────────────────────────┐
                    │  OFFICE NODE  (always-on PC)  │   ← the ONLY writer of
                    │  giams-node.exe (Axum svc)    │     ledger facts for
                    │  PostgreSQL 17 (authoritative)│     this municipality
                    │  outbox → cloud               │
                    └───────────────┬───────────────┘
                                    │  internet, when available
                                    │  manual push or scheduled
                                    ▼
                    ┌───────────────────────────────┐
                    │  CLOUD  (multi-tenant)        │
                    │  PostgreSQL + RLS per tenant  │
                    │  licensing · billing          │
                    │  consolidated reporting       │
                    └───────────────────────────────┘
```

### What each tier is allowed to do

| | Client (Tauri) | Office node | Cloud |
|---|---|---|---|
| Create **drafts** | ✅ offline | ✅ | ❌ |
| **Post** to the ledger | ❌ | ✅ **only here** | ❌ |
| Read cached reports | ✅ offline | ✅ | ✅ |
| Authoritative balances | ❌ | ✅ | replica |
| Issue document numbers | ❌ | ✅ | ❌ |

**Why drafts and postings are split.** A draft is one user's private work-in-progress —
it has no balance implications, so syncing it is trivial and conflict-free. A *posting*
is a permanent, balance-affecting fact. By allowing drafts anywhere and postings only at
the node, offline work feels unrestricted while duplication becomes structurally
impossible rather than something we defend against with cleanup scripts.

**Scenario check — the node PC is switched off.** Clerks keep drafting offline against
their local cache. When the node comes back, drafts flush and get posted. Nothing is
lost; nothing is duplicated.

**Scenario check — internet is down, WiFi is up.** Nothing changes at all. The node is
the authority; the cloud is downstream. This is requirement 2, satisfied by the topology
rather than by special-case code.

## 3. Duplication prevention

Six independent mechanisms. Any one failing does not produce a duplicate.

**1 — Identity is assigned at birth.** Every synced row has a `UUIDv7` primary key
generated by its creator. No `SERIAL` on anything that crosses a tier. Re-sending a row
is an idempotent `UPSERT` on a known id, not an insert of a new one.

**2 — Transactional outbox.** A node writes to `sync_outbox` in the *same database
transaction* as the business change. Either both commit or neither does. There is no
window where a ledger fact exists but its sync record doesn't (or vice versa).

```
sync_outbox(node_id, node_seq BIGINT, entity, entity_id,
            op, payload JSONB, payload_hash, created_at)
```

**3 — Monotonic per-node sequence.** `node_seq` increases strictly per node. The cloud
tracks `last_applied_seq` per node and applies strictly in order. A replayed batch is a
no-op; a *gap* is detected immediately and halts sync loudly instead of silently
skipping a voucher.

**4 — Batch idempotency keys.** Every push carries a `batch_id`. The cloud records
applied batch ids and returns the original result for a repeat — so a network timeout
that hides a successful response can be safely retried.

**5 — Natural-key uniqueness.** `UNIQUE (tenant_id, doc_type, doc_no)` and
`UNIQUE (tenant_id, fund_id, jev_no)`. Even if every layer above failed, the database
refuses the second copy.

**6 — Content hash + audit chain.** Each payload carries a SHA-256 of its canonical
form. The audit chain (§6) already links every record to its predecessor, so a duplicate
inserted out-of-band breaks the chain and `verify_audit_chain()` names it.

### Sync is one-directional for facts

Ledger facts flow **node → cloud** only. The cloud never writes a journal entry back
down. What flows **cloud → node** is only: licence tokens, software updates, and
reference data the tenant subscribes to. This removes the entire class of bidirectional
merge conflicts.

### User control

Settings offer: **Manual** (a "Sync now" button with a visible pending count),
**Automatic** (every N minutes when a connection is detected), or **Scheduled** (e.g.
nightly at 18:00). Default: automatic every 15 minutes, because the failure mode of
forgetting to sync is worse than the failure mode of syncing too often.

The sync status is always visible in the status bar: `Synced 3 minutes ago` /
`14 changes waiting to upload` / `No internet — working locally`.

## 4. Multi-tenancy — built in now, sold later

Retrofitting tenancy into a live financial database is the single most expensive
mistake available here. So even though subscription is the *last* feature built:

- **Every table carries `tenant_id` from migration 001.**
- **Postgres Row Level Security is on from day one**, with policies keyed to
  `current_setting('app.tenant_id')`. The connection sets it per request. A query that
  forgets a `WHERE tenant_id = …` returns nothing rather than another LGU's ledger.
- The single-municipality deployment simply has one tenant row. Nothing about the
  local experience changes.

## 5. Licensing — offline-enforceable subscription

The concept you're reaching for is a **signed offline licence token**. Think of it as a
tamper-proof certificate the app can validate with no internet at all.

**How it works.** A licensing authority (your server) holds an **Ed25519 private key**.
The desktop app ships with only the matching **public key** compiled in. A licence is a
compact signed token:

```
tenant_id · plan · seat_count · issued_at · not_before · expires_at
· hardware_fingerprint · grace_days · features[]     ── signed with Ed25519
```

The app verifies the signature locally. It cannot be forged without your private key,
and editing any field invalidates the signature. This is the same mechanism as a TLS
certificate, scaled down.

**Expiry that survives offline.**

| State | Behaviour |
|---|---|
| Valid, online | Silent renewal on check-in; token refreshed |
| Valid, offline | Full function until `expires_at` |
| Expired, within `grace_days` | Full function, persistent banner counting down |
| Past grace | **Read-only mode** — everything viewable, every report still printable, no new postings |

Never hard-lock a municipality out of its own books. A COA auditor arriving during a
lapsed subscription must still be able to print statements. Read-only degradation gets
you paid without ever holding public financial records hostage.

**Anti-tamper measures.**
- **Clock rollback detection** — a monotonic `last_seen_at` high-water mark stored
  hash-chained and in the Windows Credential Manager (DPAPI). Setting the BIOS clock
  back to 2020 is detected and treated as expiry.
- **Hardware binding** — the token binds to a hash of machine identifiers, so a licence
  file copied to another office simply doesn't validate.
- **Node-level seats** — licences bind to the office node, and the node counts active
  workstation seats. One licence per municipality, not per PC.
- **The public key is compiled into the binary**, not read from a config file anyone
  could swap.

**Build order:** the licence *check seam* goes in early (a single `LicenceGuard` layer
in the API, defaulting to "unlimited local licence"). The issuance server, billing, and
renewal UI come last, as requested. Adding a seam early costs an afternoon; adding it
late means touching every route.

## 6. Security

This is a public financial system. Treated accordingly.

**Identity & session**
- Argon2id password hashing (tuned, not defaults), password policy, forced change on
  first login, progressive lockout on failed attempts.
- Access token 15 min, in memory only — never `localStorage`.
- Refresh token 8 h, rotating (each use invalidates the previous — reuse detection
  revokes the whole session family), stored in the **Windows Credential Manager** via
  DPAPI, never on disk in plaintext.
- Server-side session registry so an administrator can revoke a session immediately.

**Authorization**
- RBAC enforced in middleware **and** re-checked in the domain layer. The UI hiding a
  button is a convenience, never a control.
- Maker–checker: `draft → submitted → certified → approved → posted`. A user may not
  approve their own document. Enforced server-side.
- Postgres RLS as the last line — even a compromised API cannot cross tenants.

**Data**
- Client-local database encrypted with **SQLCipher**, key held in DPAPI.
- Office node: full-disk encryption required; Postgres `scram-sha-256` auth only.
- TLS everywhere, including LAN (`mkcert`-issued municipal CA rolled out with the MSI).
  **Certificate pinning** on the cloud sync channel.
- **Every sync batch is signed by the originating node's own keypair.** A stolen API
  credential still cannot inject forged ledger entries — it doesn't have the node key.

**Application**
- Zod validation at the client boundary **and** independent validation server-side. The
  client is never trusted, only assisted.
- All SQL through `sqlx` compile-time-checked queries — no string concatenation reaches
  the database.
- Tauri hardening: strict CSP, minimum plugin allowlist, devtools disabled in release,
  no `shell` or arbitrary `fs` capability.
- Rate limiting on auth endpoints; generic failure messages that don't reveal whether a
  username exists.
- Dependency audit (`cargo audit`, `npm audit`) wired into CI.

**Audit**
- Hash-chained `audit_log`: `row_hash = SHA256(prev_hash ‖ canonical_payload)`.
  `verify_audit_chain()` walks it and names the first broken link.
- Posted journal entries are append-only, enforced by trigger. Corrections are
  reversing entries.
- Every auto-match in reconciliation records its tier and score — an auditor can always
  be told *why* two records were matched.

## 7. Errors — written for a clerk, not a developer

Every failure crossing the wire has this shape:

```jsonc
{
  "code": "OBLIGATION_EXCEEDS_ALLOTMENT",
  "message": "This obligation is ₱12,500.00 more than the allotment still available for MOOE under the General Fund.",
  "hint": "Ask the Budget Office to realign the allotment, or reduce the amount.",
  "fields": { "amount": "Amount is higher than the remaining balance." },
  "reference": "GSN-7QK2"
}
```

- `message` is **always plain language, always specific with real numbers.** Never a
  stack trace, never SQL, never an error class name.
- `reference` is a short correlation id also written to the server log, so support can
  find the exact failure without the user reading anything technical.
- `fields` drives inline react-hook-form field errors; `message` drives the toast.

**The rule:** if an error string names a table, a column, a constraint, a status code,
or a Rust/TypeScript type, it is a defect. Rejected in review.

Anticipated and handled explicitly, each with its own written message: no network, node
unreachable, node reachable but database down, licence expired, session expired mid-form,
period already closed, entry doesn't balance, obligation over allotment, duplicate
voucher number, stale record edited by someone else, sync conflict, disk full, printer
unavailable, malformed bank statement import, unbalanced opening balance.

**Client-side**: a React error boundary per route (never a white screen), a global
TanStack Query `onError`, retry with backoff for transient network faults only — never
for a rejected posting.

## 8. UI design system

**Direction:** clean, mature, professional. Calm and easy on the eyes but high-contrast
where it matters — numbers and status. **No shadows, no elevation effects, anywhere.**

**How hierarchy is built without shadows**
- 1px borders and background-tone steps only. Cards are `background` + `border`, never
  `box-shadow`.
- Modals: a flat scrim plus a bordered panel. Dropdowns and popovers: border only.
- The single permitted `box-shadow` in the entire codebase is the **focus ring** on
  inputs, because it is an accessibility affordance rather than decoration. Enforced by
  an ESLint/stylelint rule.

**Colour** — a warm neutral base rather than stark white (less eye strain over an
8-hour shift), one restrained accent, and semantic colour reserved strictly for meaning.

| Token | Light | Purpose |
|---|---|---|
| `bg` | `#FAFAF9` | Page canvas |
| `surface` | `#FFFFFF` | Content panels |
| `border` | `#E7E5E4` | Hairlines |
| `border-strong` | `#D6D3D1` | Emphasis, table rules |
| `text` | `#1C1917` | Primary (near-black, never `#000`) |
| `text-muted` | `#78716C` | Labels, metadata |
| `accent` | `#0F766E` | Deep teal — actions, focus |
| `success` / `warning` / `danger` | green / amber / red | **Status only.** Never decoration |

Dark mode ships too — the same tokens inverted — since some staff work early and late.

**Typography**
- UI: Inter. Amounts: **tabular numerals, mandatory** (`font-variant-numeric: tabular-nums`)
  so digits align down a column. Right-aligned, always two decimals, thousands separated.
- Negative amounts in parentheses — accounting convention, not a minus sign.
- Sentence case throughout. No ALL CAPS except statutory form titles.

**Density & input** — this is a data-entry application first.
- Compact table rows (~32px), generous form spacing.
- **Full keyboard operation is a requirement, not a nicety.** Deliberate tab order,
  numpad-friendly amount fields, `Enter` to add a ledger line, `Ctrl+S` to save,
  `Ctrl+Enter` to submit, `Esc` to cancel. A clerk should be able to key an entire JEV
  without touching the mouse.
- Target 1366×768 as the floor. Layouts must not require horizontal scrolling there.
- Every destructive or irreversible action gets a typed confirmation, not a bare "OK".

**Layout** — fixed left sidebar (module nav), a top bar carrying fund/period context
and sync status, and the working area. Voucher screens follow the *shape of the COA
paper form* so staff recognise them, while the printed output matches the official form
exactly.

## 9. Frontend stack

React 19 + TypeScript (`strict`, `noUncheckedIndexedAccess`) + Vite.

| Concern | Library |
|---|---|
| Server state | **@tanstack/react-query v5** — query-key factories per domain |
| Client/UI state | **zustand v5** with `persist` |
| Validation | **zod v4** — one schema per entity, shared between form and API boundary |
| Forms | **react-hook-form** + `@hookform/resolvers/zod` |
| Tables | @tanstack/react-table (virtualised registers) |
| Routing | react-router-dom v7 |
| Charts | Recharts |
| Styling | Tailwind, with the shadow utilities removed from the theme entirely |

Types flow from one source: Rust domain types → generated TypeScript via `ts-rs` →
consumed by Zod schemas. A field renamed in Rust breaks the frontend build immediately
rather than at runtime in the Accounting Office.

**React discipline**: colocated feature folders, custom hooks for every data access
(no `fetch` in a component, ever), `Suspense` + error boundaries per route, `memo` only
where profiled, controlled inputs via RHF, and no `useEffect` for anything derivable
during render.

## 11. Build order

Each phase ends with something demonstrable and tested.

| # | Phase | Why here |
|---|---|---|
| 0 | Toolchain, workspace, Tauri ⇄ Axum ⇄ Postgres spike | Prove the plumbing before building on it |
| 1 | **Schema + invariants + tenancy + outbox** | Balanced-entry trigger, append-only, audit chain, `tenant_id`, RLS, outbox tables. Everything downstream assumes these. Retrofitting any of them is a rewrite |
| 2 | Design system + error taxonomy + auth/RBAC | The flat component library and the plain-language error pipeline, built once, used by every screen after |
| 3 | Chart of accounts, funds, budget execution, ORS | First real module |
| 4 | Disbursement vouchers, JEV, GL posting, period close | The accounting core |
| 5 | Local cache + LAN discovery + offline drafts | Offline behaviour, on a system that already works online |
| 6 | Collections, bank reconciliation, matching engine | Module B part 1 |
| 7 | Trial balance, six GPFS statements, PDF/XLSX | Module B part 2 |
| 8 | Dashboards | Needs real data to be meaningful |
| 9 | Cloud sync service | Node → cloud shipping, cloud RLS, consolidated reporting |
| 10 | **Licensing, subscription, billing** | Last, as requested — the seam exists from phase 2 |
| 11 | Hardening, migration, installer, training | Handover |

Phase 1 is the one to not rush. Everything else is built on top of it.
